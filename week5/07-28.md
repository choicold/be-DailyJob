# be-DailyJob

> 이 회고는 작업량을 보고하기 위한 문서가 아니라,
> 오늘 내가 어떤 판단을 했고 어떤 개발 행동을 반복하거나 바꿔야 하는지 확인하기 위한
기록입니다.
> 각 항목은 길게 쓰기보다, 사실/판단/근거/다음 행동이 드러나게 구체적으로 작성하세요.

### 1. 오늘 완료한 것

- **오늘 실제로 끝낸 기능/수정/학습**
    - 조회 응답 DTO 2개, 처음에 넣은 `from()` 정적 팩터리는 뒤에 Repository를 DTO projection으로 정하면서 호출부가 사라져 제거했다.
    - `AuctionItemRepository` — 목록·상세 조회, JPQL 생성자 표현식으로 DTO를 바로 반환한다. 상태 우선 정렬(`STATUS_RANK`)과 응답 크기 상한(`MAX_SUMMARY_SIZE = 100`)
    - `CursorPageResponse.nextCursor`를 `Long` → `String`으로 변경
    - `AuctionItem` 필수 컬럼 6개에 `nullable = false`. 아직 커밋 안 함
    - 학습 — LAZY / fetch join / N+1 / 카티전 곱, `nullable`이 실제로 막는 지점, `@ManyToOne.optional`이 뭔지
  
- **(오늘의 목표 중에서) 아직 끝내지 못한 부분**
    - 목표는 `DTO → Repository → Service → Controller` 한 사이클이었는데 Repository 구현까지만 수행했다.
    - Service, Controller, `AuctionItemErrorType` 셋 다 파일이 없다.

### 2. 오늘 가장 의미있었던 기술적 판단

- **내가 내린 판단**
    - 목록 API에서 커서 페이지네이션을 걷어냈다. 전체를 상태순으로 정렬해 한 번에 반환한다.
  
- **그렇게 판단한 이유**
    - 커서가 주는 게 둘인데 이 화면에서는 둘 다 사라진다.
        1. 깊은 페이지 성능 — 커서의 이점은 인덱스를 타고 시작 위치로 점프하는 것이다. 그런데
           상태 순위를 `case` 식으로 조회 시점에 계산하면 탈 인덱스가 없다. DB가 그 방 물품을 전부 읽어 filesort하고 자른다. 1페이지든 100페이지든 정렬 비용이 같다. 오프셋과 다를 게 없다.
      
        2. 안정적인 페이지 경계 — 정렬 키가 안 변할 때만 성립한다. 여기 정렬 키에 `status`가
           있고 경매 중에 계속 바뀐다. 2페이지를 요청하는 사이 `IN_PROGRESS` → `SOLD`로 넘어가면 목록 위치가 통째로 이동한다.
      
    - 남는 건 비용뿐이었다. 복합 커서, `case` 식 상수, 순위 이중화, 커서 파싱, 깨진 커서 400 응답
  
- **고려했지만 선택하지 않은 대안**
    - **오프셋** — 정확성은 오프셋이 더 나쁘다. 1페이지를 본 뒤 항목 하나가 뒤로 밀리면
      21번째가 20번째 자리로 당겨지고, 2페이지는 21번째부터라 그 항목을 영영 못 본다. 오프셋을
      고를 이유는 "옳아서"가 아니라 어차피 둘 다 틀릴 거면 싼 쪽이라는 것뿐이다.
  
    - **프론트가 정렬** — 받은 페이지 안에서만 정렬할 수 있다. 전체를 정렬하려면 `hasNext`가
      `false`가 될 때까지 다 받아야 하는데 그러면 페이지네이션을 쓸 이유가 사라진다.
  
    - 드리프트를 실제로 없애는 방법은 페이지네이션을 안 하는 것뿐이었다. 쿼리 한 번이 곧
      하나의 스냅샷이라 그 안에서는 순서가 흔들릴 수 없다.
  
- **이 판단이 코드 품질/테스트/유지보수에 미친 영향**
    - 만들 뻔한 걸 안 만들었다 — `AuctionItemCursor` record, 커서 파싱 예외 처리, `size`
      파라미터 검증, 그에 딸린 테스트 열 몇 개. Repository는 `@Query` 두 개로 끝났다.
  
    - 대신 위험 하나를 받아들였다. 물품이 101개인 방은 사용자에게 100개로 보이고 응답은
      200이다. 오늘 내내 피해온 "조용한 실패"와 같은 모양이라는 걸 알고 받은 것이고, 상한에 닿으면
      상한을 올릴 게 아니라 페이지네이션을 다시 넣어야 한다. AI가 저렇게 말하긴 하지만 페이지네이션을 꼭 굳이 넣어야 된다라고는 생각하지 않는다. 트레이드오프를 고려해야하는 시점이라고만 생각한다.
  
    - 유효 조건은 한 경매방 물품이 한 응답에 다 내려도 되는 규모인 동안이다. 수백 개가 되면 다시 본다. 그때는 위 이유로 커서가 아니라 오프셋이다.

### 3. 가장 막혔던 문제와 해결 과정

- **문제 상황 또는 증상**
    - 목록을 상태 우선(진행중 → 대기 → 낙찰 → 유찰)으로 정렬하기로 하자 커서가 깨졌다. `WHERE
  id > 40`이 더 이상 "정렬상 40 다음"을 뜻하지 않는다.
- **처음 추측한 원인**
    - `CursorPageResponse.nextCursor`가 `Long`이라 두 값을 못 담는 게 문제라고 봤다. 커서는
      정렬 기준을 그대로 담아야 하니 정렬 기준이 둘이면 커서도 두 값이어야 한다. 타입을
      `String`으로 바꾸면 풀린다고 판단했다.
- **원인을 확인하기 위해 시도한 방법**
    - 복합 커서 SQL을 직접 써봤다. `WHERE (순위 > 2) OR (순위 = 2 AND id > 40) ORDER BY 순위,
  id LIMIT 20`. 여기까지는 성립했다.
    - 그래서 `nextCursor`를 `String`으로 바꾸고 0002로 승격했고, 이어서 인코딩 형식(`"2:40"`
      평문), 깨진 커서 응답(400), `size` 기본값·최대값, `AuctionItemCursor` record 분리까지
      설계했다.
- **실제 원인**
    - 타입이 아니었다. **커서 자체가 이 화면에 안 맞았다.**
    - 복합 커서로 쿼리는 만들어지지만, 순위를 `case` 식으로 조회 시점에 계산하는 순간 커서의
      성능 이점이 없어진다.
    - 그리고 `status`는 경매 중에 값이 바뀌는 컬럼이라 정렬 키로서 안정성 전제 자체가 안 선다.
      SQL이 돌아가는 것과 커서가 의미를 갖는 것은 다른 문제였다.
- **해결 방법**
    - 페이지네이션을 걷어냈다. `STATUS_RANK`는 `ORDER BY`에 그대로 남기고 `WHERE`의 커서
      조건과 `Limit`만 뺐다.
    - 응답은 `CommonResponse<List<Summary>>`. `CursorPageResponse`는 손대지 않고 안 쓴다.
- **다음에 비슷한 문제가 생기면 먼저 확인할 것**
    - 커서를 쓰기 전에 두 가지를 먼저 본다.
        1. **정렬 키가 조회 사이에 변하는 값인가.** 변하면 커서든 오프셋이든 경계가 흔들린다.
        2. **정렬 순서를 인덱스가 그대로 갖고 있나.** 조회 시점에 `case`로 계산하면 인덱스가
           없고, 그러면 커서를 써도 오프셋과 비용이 같다.
    - "쿼리가 성립한다"를 "설계가 맞다"로 읽지 않는다. 오늘 복합 커서 SQL이 멀쩡히 돌아간 게
      오히려 판단을 늦췄다.

### 4. 오늘 잘한 행동(개발과 관련된 것)

- **어떤 행동이었는지**
    - 안건 2(없는 `auctionRoomId` 처리)를 결론 없이 열어뒀다. 판단 기준(프론트가 "죽은 링크"와
      "물품 0개"를 다른 화면으로 그려야 한다)까지만 적고 "→ Service 단계에서 열린다"로 넘겼다.
    - 막힌 지점에서만 팠다. LAZY / fetch join / N+1 학습은 "최고 입찰자 닉네임을 목록에
      넣나"를 판단하려다 나왔고, `nullable` 학습은 `optional = false`를 붙일지 정하려다 나왔다.
    - 결정을 뒤집을 때 원문을 안 지우고 취소선과 재결정 항목을 따로 달았다.
- **그 접근이 도움이 된 이유**
    - 안건 2는 오늘 하루 동안 **유일하게 안 뒤집힌 안건**이다. 결론을 안 냈으니 뒤집힐 게
      없었다.
    - 학습 둘 다 실제로 결정을 하나씩 닫았다. LAZY는 "`ToOne`은 몇 개든 fetch join 안전"으로
      안건 6을, `nullable`은 "`optional = false`는 안 붙인다"로 오늘 마지막 결정을 닫았다. 결정을
      안 낳는 학습이었으면 낭비였을 텐데 아니었다.
    - 원문을 남겨두니 "왜 커서를 그렇게까지 팠나"가 노트에 남는다. 지웠으면 페이지네이션을
      다시 넣을 때 처음부터 다시 판단해야 한다.
- **다음에도 반복하고 싶은 점**
    - 판단 기준까지만 적고 결론을 미루는 것. 안건 2 방식을 나머지에도 쓴다.

### 5. 오늘 아쉬웠던 행동(개발과 관련된 것)

- **비효율적이었던 접근/놓치거나 부족했던 점**
    - 아직 안 만든 계층의 결정을 미리 했다. 깨진 커서 400 응답, `size` 검증 위치,
      `AuctionItemCursor` 분리 — 셋 다 Service 결정인데 Repository를 짜면서 정했다. 그리고
      Repository가 바뀌자 전부 무효가 됐다. 노트에 취소선이 네 개 붙어 있다.
    - `CursorPageResponse`를 `String`으로 바꿔 0002로 승격한 것도 같은 종류다. 공용 계약
      변경이고 팀 확인 대상인데, 그걸 쓰는 코드를 한 줄도 안 만든 상태에서 승격했고 같은 날 안
      쓰게 됐다.
    - 목표가 한 사이클이었는데 앞 두 칸에서 끝난 것도 여기서 나왔다. Service·Controller를 못
      간 게 아니라 Repository 칸에서 Service·Controller 결정을 하느라 시간을 썼다.
- **그렇게 된 원인**
    - 안건이 떠오르면 그 자리에서 닫으려 했다. "지금 짜는 코드가 이 답을 요구하는가"를 안
      물었다.
    - 열어두는 게 미완성처럼 느껴져서 그랬는데, 안건 2를 보면 열어두는 쪽이 더 정확했다.
- **다음에는 다르게 해볼 구체적인 행동**
    - 다음 세션은 Service부터 시작하되 Controller 결정은 안 끌어온다. 안건 2가 Service 진입과
      동시에 열리니 그것만 닫고, `AuctionItemErrorType`은 그때 필요한 상수 하나만 만든다.
    - `AuctionItem`의 `nullable` 변경은 DB schema 변경이라 팀 확인 대상이다.
      `CursorPageResponse` 타입 변경과 함께 아직 안 알렸다. 내일 PR 본문이나 이슈 코멘트로 옮긴다.
